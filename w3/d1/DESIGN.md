# Design Decisions

## 1. SLI choice for frontend
Instead of choosing a single metric, I combined `dom_ready < 3000ms`, `js_error = false`, and `network_error = false` into a single composite availability SLI. The reason is that the user experience (user pain) is impacted by all of these factors simultaneously. I prioritized `dom_ready` over `page load time` because `dom_ready` measures the exact moment a user can actually start interacting with the page, whereas `page load time` can be extended by non-blocking resources (like tracking scripts or slow lazy-loaded images) that don't block the core user flow. From `baseline.json`, the current composite `success_rate` is 98.61% and `dom_ready_p99_ms` is 1430ms. This shows that the 3000ms threshold is reasonable and provides enough buffer for slow networks, helping to eliminate unnecessary false positives in RUM data, which is inherently noisy.

## 2. SLO target for api
I chose the 99.9% target instead of 99% or 99.99%. According to the theoretical analysis, achieving 99.9% requires a Multi-instance, Load Balancer, and auto-failover architecture, which perfectly aligns with our current FastAPI 4-instance stack. If we push for 99.99%, the system would mandate a Multi-AZ deployment, automated runbooks, and a 24/7 on-call team, multiplying the infrastructure and ops costs by 3-10x, which is unnecessary for a standard service tier. Currently, per `baseline.json`, the API's `fail_rate` is 0.00349 (0.35%), meaning the system naturally operates at ~99.65% availability. Setting the goal to 99.9% creates healthy pressure for the development team to slightly improve reliability, whereas 99% would be too loose and 99.99% is technically and financially unfeasible at this stage.

## 3. Latency threshold p99
I decided to select 500ms as the latency threshold for calculating successful API requests. Based on `baseline.json`, the current API `latency_p99_ms` is 156ms. Choosing 500ms as the failure threshold provides a buffer that is over 3x higher than the current p99. If we set a threshold that is too strict, like 200ms, the system would constantly alert due to natural minor network jitters, creating severe alert fatigue. Conversely, picking 1s or 2s wouldn't accurately reflect user frustration. The 500ms threshold ensures that only severe performance degradations will burn the error budget.

## 4. 4xx exclusion
HTTP 4xx error codes (excluding 429 Rate Limited) were explicitly excluded from the error count because they primarily represent client-side errors or invalid external bot traffic (e.g., 400 Bad Request, 404 Not Found). If we included 4xx errors in our failure count, the SLI would falsely drop without reflecting the actual health of the platform. For example, by excluding 4xx, our API `fail_rate` in `baseline.json` is accurately low at 0.00349 (0.35%), which perfectly allows us to set a tight 99.9% SLO. Only the 429 status code is counted as a system failure because it represents the system reaching maximum capacity and actively rejecting legitimate requests. In reality, 4xx errors often make up a significant portion of traffic due to web crawlers scanning non-existent endpoints.

## 5. MWMBR tuning
To optimize the time-to-detect and achieve an `mttd_delta_s` strictly below 60s, I tuned the Tier 1 burn rate threshold from the Google default of 14.4 down to 10. By lowering this threshold, the alert fires slightly earlier during a steep error rate spike (requiring 1.4% budget burn per hour instead of 2%). According to the validation output, this tuning successfully reduces the detection delay, while still keeping false positives low (`fp` = 0) and maintaining zero false negatives (`fn` = 0). This proves that lowering the Tier 1 threshold provides faster detection without compromising precision on this dataset.
